# Уточнения и оговорки к статическому аудиту (QA / Security)

Документ фиксирует границы анализа, предположения и случаи, когда вывод может не совпасть с боевым Supabase без просмотра реальной БД и рантайма.

---

## 1. Ограничения метода (статический анализ)

- Анализ выполнялся **по дереву репозитория** (TS/TSX, SQL миграции в `supabase/migrations`). **Не** выполнялись penetration-тесты, нагрузка, проверки в браузере/Telegram и **не** снимался дамп живой схемы проекта на Supabase Dashboard.
- Поведение **PostgREST/RLS после ручных правок** в Dashboard не видно из git: политики, триггеры, значения по умолчанию для колонок, расширения (`pgcrypto`, `uuid-ossp`) могут отличаться от файлов миграций.

---

## 2. Расхождение миграций в репо и боевой БД (ключевое уточнение)

Часть критических замечаний опирается на **локальные** SQL файлы. Если на продакшене таблицы уже изменялись вручную (DEFAULT для `id`, триггеры генерации `id`, переименования колонок), то:

- **INSERT без `id`** в `chat_messages` или в `dental_clients` может **успешно работать на проде** и одновременно **ломаться на новом окружении**, развёрнутом только из репозитория.
- Рекомендация всё равно валидна: в репозитории должно быть описано то же состояние, что и на проде, иначе dev/staging воспроизводят ошибки прод не видит (или наоборот).

**Итог:** формулировка из аудита — *«упадёт на чистой БД по миграциям из репо»*. Для живого проекта полезно **сверить** `information_schema`/DDL в Supabase с миграциями.

---

## 3. `client_id` в `appointments` и телефон

Замечание про FK `client_id` → `dental_clients(id)` при вставке **нормализованного телефона** остаётся силой только если **`dental_clients.id` действительно не является этим номером** (типично — случайный/генерируемый текстовый или UUID-подобный id).

Обратное уточнение (спекуляция): если архитектурное решение клиники — **явно хранить `id клиента == нормализованный телефон`** при создании строки клиента (через не зафиксированный в наших миграциях триггер/ручную вставку), тогда FK формально согласован, но смешиваются понятия **идентификатора** и **телефона** — это упрощает ошибки при смене номера и фильтрах в коде (`getAppointments` и т.д.).

Без экспорта схемы/пример строк **нельзя** на 100% утверждать, какой режим у вас на проде.

---

## 4. Магический номер администратора: длина цифр

В репозитории и правилах зафиксирован **`77777777777` (11 цифр)**. Если в задаче участниками подразумевался **`7777777777` (10 семёрок после +7 без ведущей 7 страны или иная семантика)**, возможны два эффекта:

- UI требует **11** значащих цифр на шаге телефона — «короткий» паттерн из ТЗ мог **вообще не пройти** валидацию.
- Совпадение с сидом `dental_employees.phone` возможно только при том же строковом представлении, что в базе (`ilike` по суффиксу из `lib/auth.ts` всё же обычно матчится по последним 10 цифрам; детально зависит от того, что хранится в поле `phone`).

Это не баг исполнения кода автоматически, а уточнение **соответствия ТЗ ↔ данные ↔ валидация длины**.

---

## 5. Безопасность анонима и «насколько это баг именно вашего приложения»

Критика **RLS с `USING (true)`** для `anon`: на практике многие мини-приложения временно живут именно так, полагаясь на сокрытие URL и ограниченный ключ. Уточнение: это **архитектурный и правовой риск**, а не обязательно «сейчас падающий функциональный баг».

Риск становится тем выше, чем проще восстановить `NEXT_PUBLIC_SUPABASE_URL` + `NEXT_PUBLIC_SUPABASE_ANON_KEY` из бандла (это тривиально для клиентского приложения).

---

## 6. Демо OTP и вход по коду без SMS

Вывод про слабую аутентификацию описывает **текущую реализованную механику** (демо-коды, переход без реальной SMS при известном сценарии). Уточнение: если продукт **намеренно** демо/внутренний, это может быть приемлемо; для публичного Telegram Mini App с ПДн пациента — нужна явная политика (реальный OTP или `initData` + backend).

---

## 7. Realtime unsubscribe и «утечка»

Эффект **отсутствия `unsubscribe` при размонтировании до конца async** — реальный паттерн-риск, но **тяжесть зависит** от частоты монтирования/размонтирования страницы и лимита каналов Supabase клиента; не измерялось профилировщиком.

---

## 8. Конфликт гайдов (зелёный в галочке успеха записи)

В аудите упомянут цвет галочки, конфликтующий с `.cursor/rules`. Уточнение: там же есть формулировка про допустимый «системный зелёный для успеха» — при разрешении противоречия внутри правил нужна **единая трактовка** владельцем продукта; технически это не security issue.

---

## 9. Битрикс и «остаточный код»

Поиск по `*.ts`/`*.tsx` не нашёл активного кода CRM Bitrix; упоминания — в правилах/`.gitignore`. Уточнение: **закешированный** функционал вне этих паттернов (другая ветка, непросмотренная папка, бинари) аудитом не покрывался.

---

## 10. Сводная формула доверия к выводу

| Вывод аудита                              | Если только миграции из репо | Если прод с ручными фиксами |
| ----------------------------------------- | ---------------------------- | ---------------------------- |
| `chat_messages` INSERT без `id`           | Высокая вероятность ошибки    | Зависит от DEFAULT/trigger    |
| `dental_clients` INSERT без `id`          | Аналогично                    | Зависит от DEFAULT/trigger    |
| `client_id`: телефон vs FK на `clients.id`| Риск неконсистентности       | Единственный источник — DDL + данные |
| Анонимные RLS                             | По миграциям — да            | Если политики ужесточили — уже другое |
